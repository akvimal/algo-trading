# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-system algo-trading platform, loosely coupled by design: `signal-generation`, `signal-processing`, `execution`, `market-data`. Full architecture and roadmap: `docs/architecture.md`. All four have a backend now. `signal-generation` owns the **Strategy** entity (CRUD + webhook URLs); its engine/backtesting integration and in-house signal generation are still planned — see its `README.md`.

## Commands

Root (docker-compose based):
```
cp .env.example .env && make bootstrap        # first-time setup: build + up + prints service URLs (base stack only)
docker compose --profile execution up -d --build   # also bring up execution (needs Dhan creds in .env for real quotes)
make up / make down / make logs / make ps / make build
make psql                                      # psql shell into postgres
make test-signal                               # simulate a Chartink webhook alert end-to-end (scripts/simulate-chartink-alert.sh [buy|sell] [strategy_id] - auto-creates a throwaway strategy if none given)
```

**Two isolated local container groups**: `make up`/`down`/`logs`/`ps`/`build`/`psql` above always target **dev** (project `algo-trading`, ports from `.env` - 8000-8003/8080-8082/8090, postgres 5433, redis 6379). A second, fully separate **test** stack runs alongside it on the same machine — same `docker-compose.yml`, different Compose project name and `.env.test` (every port is dev's + 1000, e.g. signal-processing backend 9000, its frontend 9080) — own containers/volumes/network, no data or state shared with dev: `make test-up` / `test-down` / `test-build` / `test-logs` / `test-ps` / `test-psql`. `.env.test` is gitignored, same as `.env`. Known gap: cross-system deep links (`src/links.ts` in each frontend) hardcode the *dev* frontend ports, so links generated inside the test stack still point at dev's frontends — a pre-existing simplification (see "Cross-linking between frontends" below), not fixed by the dev/test split.

Any Python backend (`systems/{signal-processing,execution,market-data,signal-generation}/backend`):
```
python -m venv .venv && .venv/Scripts/python -m pip install -r requirements-dev.txt   # Windows; use bin/activate elsewhere
pytest -q                                       # all tests
pytest tests/test_position_manager.py -q        # single file, e.g. in execution
```

Any React frontend (`systems/{signal-processing,execution,signal-generation}/frontend`):
```
npm install
npm run dev      # vite dev server; point VITE_API_BASE_URL at http://localhost:<backend-port> in a local .env - the nginx /api proxy only exists inside the container
npm run build     # tsc -b && vite build (type-checks then builds)
```

## Architecture

- Systems in `systems/` are self-contained — **no direct imports between `systems/*` folders**. Cross-system communication is only an HTTP call against a versioned JSON contract (`docs/contracts/*.schema.json`) or a Redis stream, never a shared DB table or shared code. Each system that holds business-critical state owns its own Postgres schema (`infra/postgres/init/*.sql`); `market-data` holds none by design (in-memory cache only, see its README).
- **Strategy is the unit of configuration for a signal source** (external webhook provider or in-house engine), owned by `signal-generation` (`signal_generation.strategies`). It's what signal-processing's resolution actually resolves *to* — `horizon`/`instrument_type` come from the strategy the signal names, not from guessing. It deliberately carries **no quantity/capital field** — see position sizing below. Not to be confused with signal-processing's unrelated *option-strategy* selection (spread/straddle, `app/domain/resolution/strategy.py`) — see `docs/architecture.md` § "Strategy: the unit of configuration for a signal source" for the disambiguation.
- **Intake flow**: provider (e.g. Chartink) → a webhook route directly on `signal-processing` (`app/api/routes/webhooks.py`, `?strategy_id=<uuid>`, one route pair per provider, **not** per strategy — the query param scopes it) → archives the raw payload (`archive_raw_payload`) → normalizes/fans-out multi-symbol alerts into the canonical shape (`app/domain/intake/<provider>.py`, includes `strategy_id`, `price`, `exchange`) → calls `create_signal_from_ingest` in-process (the same function `POST /signals` itself calls) → persists the signal, resolves it by calling `GET /strategies/{id}` on signal-generation (`app/domain/resolution/pipeline.py`) → if the strategy is missing/unreachable/not `live`, persists as `rejected` with a reason and **does not publish to Redis**; otherwise persists the resolved order and `XADD`s it to `orders.resolved`.
- **Execution flow**: a Redis consumer group in `execution/backend` reads `orders.resolved` (at-least-once, idempotent on `signal_id` — see `app/consumers/orders_consumer.py` and `app/domain/position_manager.open_position`), opens a paper position at the signal's price for `intraday`+`spot`/`future` orders only (anything else is `REJECTED` with a reason), and an APScheduler job inside the same service closes every open position at a configurable `square_off_time` using CMP from `market-data`. `square_off_time`/`capital_per_trade` are DB-backed and editable via `GET`/`PUT /settings` (execution) or per-account — changing the time reschedules the job immediately. **Signal-conflict handling is per-strategy, not a global execution setting**: `Strategy.duplicate_signal_policy` (`skip`/`add_position`, default `add_position`) governs a same-direction signal arriving while a position is already open on that symbol (reject vs. pyramid an independent additional position), and `Strategy.counter_signal_policy` (`skip`/`close_and_flip`, default `skip`) governs an opposite-direction signal (leave the existing position alone vs. close it — `exit_reason='counter_signal'`, synchronously, ahead of its own stop-loss/target/square-off — then open the new one). Both are carried through unchanged on the resolved order (`app/domain/position_manager._resolve_signal_conflicts`), same passthrough mechanism as the stop-loss/target fields below.
- **Position sizing lives in execution, not signal-generation.** `quantity = floor(capital_per_trade / signal_price)`, computed in `position_manager.compute_quantity()` when a position opens - `resolved-order.schema.json` carries no quantity at all. If that comes out to 0 shares, it floors to 1 share instead - a position always opens rather than being rejected for undersized capital (same floor for the risk-based sizing path, `compute_risk_based_quantity`). Global setting for now, not per-strategy - see `docs/architecture.md` § "Why position sizing lives in execution, not signal-generation".
- **market-data** is the one place provider credentials/instrument-master sync live, so `execution` (and later signal-generation's in-house engine) call `GET /quotes/ltp?exchange=NSE&symbol=X` instead of each embedding a broker SDK. Only Dhan/NSE is implemented; MCX and crypto (Delta Exchange) are routed-but-unimplemented in `app/providers/router.py`. Dhan's LTP endpoint is rate-limited - `DhanProvider` self-throttles (2s min gap).
- **Provider intake is intentionally thin**: webhook receipt, raw-payload archival, provider-shape normalization/fan-out only, directly in `signal-processing` (`app/api/routes/webhooks.py` + `app/domain/intake/`) — it passes `strategy_id` through unchanged, it never looks a strategy up itself. All trade-classification logic is plain Python elsewhere in the same backend, not the intake layer — see `docs/architecture.md` § "Why Chartink intake lives directly in signal-processing" (this used to run in n8n, a separate service, until it was replaced with this direct implementation). Execution's square-off scheduler is similarly self-contained (`APScheduler` inside `execution/backend`, see `docs/architecture.md` § "Why the square-off scheduler lives in execution, not a separate orchestrator") so a 15:00 trigger doesn't depend on a second service being up.
- **Contracts are the seam.** `docs/contracts/signal-ingest.schema.json` and `resolved-order.schema.json` are versioned like an API. Each consuming backend's `app/domain/models.py` is a hand-written Pydantic mirror — if you change a contract, update every mirror (there's no codegen wiring them together yet). The `contract-guardian` agent (`.claude/agents/`) checks for this drift.
- **Chartink specifics**: one webhook path per direction (`/webhook/chartink-buy`, `/webhook/chartink-sell`) on `signal-processing`, each accepting `?strategy_id=` for any strategy - not one route per strategy (a query param is simpler than sprawling routes, and is required - FastAPI 422s a request missing it). `exchange: "NSE"` hardcoded in `app/domain/intake/chartink.py`'s route handler since Chartink scans in this repo are NSE-only. A single alert carries comma-separated `stocks`/`trigger_prices`, fanned out (`parse_chartink_alert`) into individual canonical signals before they ever reach the resolution pipeline; one bad symbol (missing/unparseable price) is skipped, not allowed to abort the rest of the alert.
- **Cross-linking**: every frontend table row that has a `signal_id` links to that same signal's view in the other frontends (`?signal_id=<uuid>` deep link, each frontend filters to it on load). Ports are hardcoded per-frontend in a small `src/links.ts` — update those three files if you change a `*_FRONTEND_PORT`. `signal-generation`'s frontend reads signal-processing's `GET /signals?strategy_id=X` directly from the browser (CORS) for per-strategy signal activity rather than owning a copy of that data — see `docs/architecture.md` § "Cross-linking between frontends".
- **DB schema lives in SQL, not the ORM.** `infra/postgres/init/{01-signal-processing,02-execution,03-signal-generation}.sql` is what actually creates the tables (run once, on first container start against a fresh volume). Each backend's `app/adapters/db/models.py` is a hand-maintained SQLAlchemy mirror — there's no Alembic and no `metadata.create_all()`. Adding a column means updating both files, and existing Postgres volumes need the SQL applied manually (or the volume recreated) since init scripts don't re-run.
- `docker-compose.yml` wires up `postgres`, `redis`, `signal-processing-{backend,frontend}`, `market-data-backend`, `signal-generation-{backend,frontend}` (all infra-tier, always up, no profile), and `shell` (static tab nav) unconditionally. `execution-{backend,frontend}` sit behind `profiles: ["execution"]` — bring them up with `docker compose --profile execution up -d`.
