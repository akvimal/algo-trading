# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-system algo-trading platform, loosely coupled by design: `signal-generation`, `signal-processing`, `execution`, `market-data`. Full architecture and roadmap: `docs/architecture.md`. All four have a backend now. `signal-generation` owns the **Strategy** entity (CRUD + webhook URLs); its engine/backtesting integration and in-house signal generation are still planned — see its `README.md`.

## Commands

Root (docker-compose based):
```
cp .env.example .env && make bootstrap        # first-time setup: build + up + prints service URLs (base stack only)
docker compose --profile execution up -d --build   # also bring up execution (needs Dhan creds in .env for real quotes)
make up / make down / make logs / make ps / make build
make psql                                      # psql shell into postgres
make test-signal                               # simulate a Chartink webhook alert end-to-end (scripts/simulate-chartink-alert.sh [buy|sell] [strategy_id] - auto-creates a throwaway strategy if none given)
```

**Two isolated local container groups**: `make up`/`down`/`logs`/`ps`/`build`/`psql` above always target **dev** (project `algo-trading`, ports from `.env` - 8000-8003/8080-8082/8090, postgres 5433, redis 6379). A second, fully separate **test** stack runs alongside it on the same machine — same `docker-compose.yml`, different Compose project name and `.env.test` (every port is dev's + 1000, e.g. signal-processing backend 9000, its frontend 9080) — own containers/volumes/network, no data or state shared with dev: `make test-up` / `test-down` / `test-build` / `test-logs` / `test-ps` / `test-psql`. `.env.test` is gitignored, same as `.env`. Known gap: cross-system deep links (`src/links.ts` in each frontend) hardcode the *dev* frontend ports, so links generated inside the test stack still point at dev's frontends — a pre-existing simplification (see "Cross-linking between frontends" below), not fixed by the dev/test split.

Any Python backend (`systems/{signal-processing,execution,market-data,signal-generation}/backend`):
```
python -m venv .venv && .venv/Scripts/python -m pip install -r requirements-dev.txt   # Windows; use bin/activate elsewhere
pytest -q                                       # all tests
pytest tests/test_position_manager.py -q        # single file, e.g. in execution
```

Any React frontend (`systems/{signal-processing,execution,signal-generation,manual-trading}/frontend`):
```
npm install
npm run dev      # vite dev server; point VITE_API_BASE_URL at http://localhost:<backend-port> in a local .env - the nginx /api proxy only exists inside the container
npm run build     # tsc -b && vite build (type-checks then builds)
```

## Architecture

- Systems in `systems/` are self-contained — **no direct imports between `systems/*` folders**. Cross-system communication is only an HTTP call against a versioned JSON contract (`docs/contracts/*.schema.json`) or a Redis stream, never a shared DB table or shared code. Each system that holds business-critical state owns its own Postgres schema (`infra/postgres/init/*.sql`); `market-data` holds none by design (in-memory cache only, see its README).
- **Strategy is the unit of configuration for a signal source** (external webhook provider or in-house engine), owned by `signal-generation` (`signal_generation.strategies`). It's what signal-processing's resolution actually resolves *to* — `horizon`/`instrument_type` come from the strategy the signal names, not from guessing. It deliberately carries **no quantity/capital field** — see position sizing below. Not to be confused with signal-processing's unrelated *option-strategy* selection (spread/straddle, `app/domain/resolution/strategy.py`) — see `docs/architecture.md` § "Strategy: the unit of configuration for a signal source" for the disambiguation.
- **Rule is the unit of *when a signal fires*, split out of Strategy, and is in-house only** (`signal_generation.rules`, `app/domain/rule.py`) — the underlying/universe, interval, condition (crossover/breakout/range_breakout), and regime filter (`regime_indicator_ids`, 5 dedicated `IndicatorType`s - `structure`/`efficiency_ratio`/`adx`/`dmi_direction`/`ema_slope` - see `app/domain/regime.py`) all live there. A Strategy references one via `rule_id`, required exactly for `source_type='in_house'` and forbidden otherwise (`validate_strategy_rule_requirement`) - an external (webhook) Strategy carries its own `source_type` directly and has no Rule at all, since the provider decides when a signal fires. One Rule can back many Strategies. Backtest moved with it (`POST /rules/{id}/backtest`, not `/strategies/{id}/backtest`) — see `docs/architecture.md` § "Rules module" and § "Market regime filter" for the full design, including why `EngineRun` dedup state stays keyed by `strategy_id`.
- **Intake flow**: provider (e.g. Chartink) → a webhook route directly on `signal-processing` (`app/api/routes/webhooks.py`, `?strategy_id=<uuid>`, one route pair per provider, **not** per strategy — the query param scopes it) → archives the raw payload (`archive_raw_payload`) → normalizes/fans-out multi-symbol alerts into the canonical shape (`app/domain/intake/<provider>.py`, includes `strategy_id`, `price`, `exchange`) → calls `create_signal_from_ingest` in-process (the same function `POST /signals` itself calls) → persists the signal, resolves it by calling `GET /strategies/{id}` on signal-generation (`app/domain/resolution/pipeline.py`) → if the strategy is missing/unreachable/not `live`, persists as `rejected` with a reason and **does not publish to Redis**; otherwise persists the resolved order and `XADD`s it to `orders.resolved`. The not-`live` check is skipped for `source="manual"` signals only (the frontend's "Send test signal"/Manual tab) — lets a strategy be exercised end-to-end while still `draft`/`backtesting`/`paused`, before promoting it to `live`; every other rejection reason and every other source (`chartink`, `in_house`) is unaffected.
- **Execution flow**: a Redis consumer group in `execution/backend` reads `orders.resolved` (at-least-once, idempotent on `signal_id` — see `app/consumers/orders_consumer.py` and `app/domain/position_manager.open_position`), opens a paper position at the signal's price for `intraday`+`spot`/`future` orders only (anything else is `REJECTED` with a reason), and an APScheduler job inside the same service closes every open position once local time passes **its own segment's** configured `square_off_time` (`execution.accounts.square_off_time` — one per segment, `NULL` allowed and means that segment never force-closes, e.g. CRYPTO's default, since crypto trades 24/7) using CMP from `market-data`. `square_off_time`/`capital_per_trade` are DB-backed and editable via `GET`/`PUT /accounts/{segment}` — no reschedule step needed, both periodic jobs (square-off, exit-monitor) just poll and read current data fresh. `square_off_time` used to be a required per-`Strategy` field (signal-generation) — moved here since it's a market-hours concept, not a per-strategy one; `Strategy` no longer carries any square-off concept at all, only its own `active_from_time`/`active_to_time` (which purely gates whether a signal is *accepted*, with no further effect on the resulting position). **Signal-conflict handling is per-strategy, not a global execution setting**: `Strategy.duplicate_signal_policy` (`skip`/`add_position`, default `skip`) governs a same-direction signal arriving while a position is already open on that symbol (reject vs. pyramid an independent additional position), and `Strategy.counter_signal_policy` (`skip`/`close_and_flip`, default `close_and_flip`) governs an opposite-direction signal (leave the existing position alone vs. close it — `exit_reason='counter_signal'`, synchronously, ahead of its own stop-loss/target/square-off — then open the new one). Both are carried through unchanged on the resolved order (`app/domain/position_manager._resolve_signal_conflicts`), same passthrough mechanism as the stop-loss/target fields below.
- **Position sizing lives in execution, not signal-generation.** `quantity = floor(capital_per_trade / signal_price)`, computed in `position_manager.compute_quantity()` when a position opens - `resolved-order.schema.json` carries no quantity at all. If that comes out to 0 shares, it floors to 1 share instead - a position always opens rather than being rejected for undersized capital (same floor for the risk-based sizing path, `compute_risk_based_quantity`). Global setting for now, not per-strategy - see `docs/architecture.md` § "Why position sizing lives in execution, not signal-generation". One deliberate, explicit exception: `Strategy.fixed_lots` (optional, every `instrument_type` - renamed from `option_fixed_lots`, which used to be options-only, widened 2026-08-15), which when set overrides auto-sizing entirely (takes precedence over stop-loss-based sizing too) - number of lots, not raw underlying units (a no-op distinction for spot, real for futures/options; labeled "Qty" for spot and "Lots" for future/option in the frontend) - see that doc section's `fixed_lots` subsection. **CRYPTO positions convert `effective_capital` (INR) to USD-equivalent before sizing** (never the price/stop-loss/target, which stay native USD) using `execution.settings.usdinr_rate` - a manually configured rate (`GET`/`PUT /settings`, execution's own Settings page), not a live feed - NSE's currency-futures segment had no unexpired contract to source one from when this was built. See that doc section's USDINR subsection. **CRYPTO also supports leverage** - `execution.accounts.leverage` (default 1, `GET`/`PUT /accounts/CRYPTO`) multiplies the USD-converted capital before sizing, matching Delta Exchange India's own margin model (`funds_req = notional / leverage`); scoped to spot/future (`position_manager.open_position`) only, not options - see that doc section's leverage subsection.
- **`manual-trading` is its own frontend-only system** (`systems/manual-trading/frontend`, no backend of its own) holding the Manual Trading tab and the Options OI summary - split out of `signal-generation`'s frontend 2026-08-26 (see `docs/architecture.md` § "Manual Trading module split") once it became clear neither ever actually depended on signal-generation's own backend/DB, only on `execution`'s and `market-data`'s directly from the browser (same CORS pattern every frontend already uses cross-system). Manual Trading places paper trades independent of any saved Strategy - both spot/future (`POST /positions/manual`) and option orders (naked/spread, `POST /option-groups/manual`) go straight to `execution`, bypassing signal-generation/signal-processing entirely (`positions.strategy_id`/`option_position_groups.strategy_id` both nullable, `NULL` = manually opened - no auto-provisioned Strategy for either instrument type anymore). Options resolve their own legs directly in execution (`app/domain/option_position_manager.py`'s `open_manual_option_group`, using a ported copy of signal-processing's `option_templates.py` leg-selection logic) against the nearest currently-tradeable expiry, resolved server-side via `GET /options/expiries` - there used to be a frontend Expiry dropdown backing a user-picked value instead, but that call proved slow/unreliable enough as a blocking frontend dependency (stuck on "Loading..." indefinitely) that it was removed 2026-08-14 in favor of silent-auto-nearest (matching the pre-2026-08-14 Strategy-mediated path's own behavior); `ManualOptionGroupCreate.expiry` is still accepted as an optional override, just no longer surfaced in the UI. Also added: partial square-off (`?quantity=` on `POST /positions/{id}/square-off`, spot/future only) and editable stop-loss on an already-open position (`PUT /positions/{id}/stop-loss`, `PUT /option-groups/{id}/stop-loss`). See `docs/architecture.md` § "The Manual tab" for the full design, including the trigger-price semantics (a browser-side watch, not a persisted pending order). Its `SignalNotifier` component is deliberately duplicated (not shared) from signal-generation's own copy - small enough that copying beats adding a cross-system frontend dependency.
- **market-data** is the one place provider credentials/instrument-master sync live, so `execution` (and signal-generation's in-house engine) call `GET /quotes/ltp?exchange=NSE&symbol=X` instead of each embedding a broker SDK. NSE/MCX via Dhan (`DhanProvider`, credentialed, rate-limited - self-throttles with a 2s min gap) and CRYPTO via Delta Exchange India (`DeltaProvider`, Phase 1 of the crypto module - fully public endpoints, no credentials needed at all) are both implemented; option chain/execution for CRYPTO are still planned. Dhan's LTP endpoint is rate-limited - `DhanProvider` self-throttles (2s min gap).
- **Provider intake is intentionally thin**: webhook receipt, raw-payload archival, provider-shape normalization/fan-out only, directly in `signal-processing` (`app/api/routes/webhooks.py` + `app/domain/intake/`) — it passes `strategy_id` through unchanged, it never looks a strategy up itself. All trade-classification logic is plain Python elsewhere in the same backend, not the intake layer — see `docs/architecture.md` § "Why Chartink intake lives directly in signal-processing" (this used to run in n8n, a separate service, until it was replaced with this direct implementation). Execution's square-off scheduler is similarly self-contained (`APScheduler` inside `execution/backend`, see `docs/architecture.md` § "Why the square-off scheduler lives in execution, not a separate orchestrator") so a 15:00 trigger doesn't depend on a second service being up.
- **Contracts are the seam.** `docs/contracts/signal-ingest.schema.json` and `resolved-order.schema.json` are versioned like an API. Each consuming backend's `app/domain/models.py` is a hand-written Pydantic mirror — if you change a contract, update every mirror (there's no codegen wiring them together yet). The `contract-guardian` agent (`.claude/agents/`) checks for this drift.
- **Chartink specifics**: one webhook path per direction (`/webhook/chartink-buy`, `/webhook/chartink-sell`) on `signal-processing`, each accepting `?strategy_id=` for any strategy - not one route per strategy (a query param is simpler than sprawling routes, and is required - FastAPI 422s a request missing it). `exchange: "NSE"` hardcoded in `app/domain/intake/chartink.py`'s route handler since Chartink scans in this repo are NSE-only. A single alert carries comma-separated `stocks`/`trigger_prices`, fanned out (`parse_chartink_alert`) into individual canonical signals before they ever reach the resolution pipeline; one bad symbol (missing/unparseable price) is skipped, not allowed to abort the rest of the alert.
- **Cross-linking**: every frontend table row that has a `signal_id` links to that same signal's view in the other frontends (`?signal_id=<uuid>` deep link, each frontend filters to it on load). Ports are hardcoded per-frontend in a small `src/links.ts` — update those three files if you change a `*_FRONTEND_PORT`. `signal-generation`'s frontend reads signal-processing's `GET /signals?strategy_id=X` directly from the browser (CORS) for per-strategy signal activity rather than owning a copy of that data — see `docs/architecture.md` § "Cross-linking between frontends".
- **DB schema lives in SQL, not the ORM.** `infra/postgres/init/{01-signal-processing,02-execution,03-signal-generation}.sql` is what actually creates the tables (run once, on first container start against a fresh volume). Each backend's `app/adapters/db/models.py` is a hand-maintained SQLAlchemy mirror — there's no Alembic and no `metadata.create_all()`. Adding a column means updating both files, and existing Postgres volumes need the SQL applied manually (or the volume recreated) since init scripts don't re-run.
- `docker-compose.yml` wires up `postgres`, `redis`, `signal-processing-{backend,frontend}`, `market-data-backend`, `signal-generation-{backend,frontend}` (all infra-tier, always up, no profile), and `shell` (static tab nav) unconditionally. `execution-{backend,frontend}` sit behind `profiles: ["execution"]` — bring them up with `docker compose --profile execution up -d`. `manual-trading-frontend` sits behind that same profile (it's non-functional without execution running) despite having no backend of its own.
