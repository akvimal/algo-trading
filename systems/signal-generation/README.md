# signal-generation

Owns the **Strategy** entity: the unit of configuration for anything that produces a BUY/SELL idea - external scanners (Chartink, TradingView, ...) or an in-house indicator engine. Both `backend/` and `frontend/` are fully built, including the in-house engine.

## Strategy CRUD + webhook URLs

`backend/` owns `signal_generation.strategies` - `POST /strategies` to create one (`name`, `source_type`, `horizon`, `instrument_type`, optional `interval`), `GET /strategies/{id}` (also used by signal-processing during resolution - see `docs/architecture.md`), `PATCH /strategies/{id}` to change `status` or config. New strategies start `draft`; signal-processing rejects any signal for a non-`live` strategy, so creating one and getting webhook URLs doesn't start trading until you explicitly activate it. `interval` (1min/3min/5min/15min/30min/60min/daily) is optional and purely descriptive for webhook providers (we don't control when Chartink fires); for an `in_house` strategy it's required and drives the engine's own check cadence and candle granularity. Any `Nmin` value Dhan doesn't natively serve (3min, 30min, ...) is served transparently via market-data's local aggregation of native 1min bars - see `docs/architecture.md` § "Why market-data is its own system".

No position-size/capital field here on purpose - `execution` sizes every position itself from its own account's `capital_per_trade`/`risk_per_trade_pct` and the signal's price, the same for every strategy. See `docs/architecture.md` § "Why position sizing lives in execution, not signal-generation".

`frontend/` has three tabs:

- **Chartink** - create/list strategies, copy their webhook URLs (`/webhook/chartink-{buy,sell}?strategy_id=<id>` on signal-processing's own backend - the *same* two routes handle every Chartink strategy, scoped by that query param, not one route per strategy), activate/pause, and see recent signals per strategy cross-linked to signal-processing and execution (`?signal_id=` deep links, see `src/links.ts`).
- **TradingView** - "not configured" placeholder; wiring one up follows the same pattern as Chartink (`add-signal-provider` skill) - no route exists for it yet.
- **In-house** - manage reusable **Indicators** (e.g. "RSI 14") and `in_house` strategies (underlying + which indicator + rule), plus a backtest panel per selected strategy - see below.

## Indicators and the in-house engine

Indicators are their own entity - `signal_generation.indicators` (`name`, `type`, `params` - `{"type": "rsi", "params": {"period": 14, "sma_period": 9}}` today), managed via `POST/GET/PATCH/DELETE /indicators`. Defining "RSI 14" once and letting any number of strategies reference it (rather than each strategy embedding its own copy of RSI's params) is deliberate - see `docs/architecture.md` § "Indicators are decoupled from Strategy". `sma_period` - RSI's own signal line - is bundled into the indicator's own params rather than the rule, matching how TradingView's RSI script bundles "RSI Length" and "MA Length" together; editing it via `PATCH /indicators/{id}` changes it for every strategy referencing that indicator at once.

Built fresh in Python inside `backend/` (no separate service, no submodule):
- `app/domain/indicators.py` - pure indicator math (`compute_rsi`, `compute_sma`) plus the per-type dispatchers `compute_indicator(type, params, closes)` (the primary value), `compute_indicator_signal(type, params, closes)` (the indicator's own signal line, e.g. SMA-of-RSI), and `indicator_warmup(type, params)`. A second indicator type is new code here only.
- `app/domain/rules.py` - `evaluate_crossover(value_series, signal_series)`, deliberately generic (just "value crosses signal", knows nothing about RSI or how the signal series was derived), plus the top-level `evaluate(rule, indicator_type, indicator_params, candles)` / `bars_needed(...)` dispatchers a `Strategy`'s rule actually calls. A second rule type is new code here only.
- `app/domain/engine.py` (the live tick), `app/domain/backtest.py` (signal replay + trade simulation, see below) - both call the **exact same** `rules.evaluate()`, so they can never silently disagree about what counts as a signal.

An `in_house` Strategy adds two fields beyond the webhook ones: `underlying` (e.g. `"GOLDM"`, `"NIFTY"`) and `rule_config` (a typed JSON blob naming *which* indicator the rule uses - `{"type": "crossover", "indicator_id": "<uuid>"}` today, no parameters of its own since the signal line is the indicator's concern; adding a second rule type later is new code, not a schema migration, since this is JSONB, not dedicated columns). The API checks `indicator_id` resolves to a real `Indicator` at strategy create/update time; if that indicator is later deleted, the engine defensively skips the strategy on its next tick rather than crashing.

A periodic job (`app/scheduler.py`, own `IntervalTrigger`, default 60s - independent of any one strategy's own `interval`) checks every `status='live', source_type='in_house'` Strategy:

1. Resolves the underlying via `market-data`'s `GET /instruments/resolve?segment=&underlying=` - what to chart indicators on (`chart_symbol`) and what to actually trade (`trade_symbol`). Equal for MCX commodity futures (no continuous spot - chart and trade the same active-month contract); different for NSE indices (chart the continuous index spot, trade the active-month index future - see `docs/architecture.md`).
2. Fetches enough recent history via `market-data`'s `GET /candles/history` to warm up the indicator.
3. Runs `rules.evaluate()`; if the latest completed bar shows a fresh crossover it hasn't already acted on (tracked per-strategy in `signal_generation.engine_runs`, so the same bar never re-signals every poll tick), it `POST`s to signal-processing's `/signals` - the exact same contract every webhook provider's own intake route uses, so nothing downstream needs to know this signal came from an in-house rule instead of Chartink.

**Backtesting** (`POST /strategies/{id}/backtest?from=&to=`) simulates a paper trade per signal, not just raw signal timing: it fetches history for the range and, for each fresh crossover `rules.evaluate()` finds, opens a simulated trade and closes it the same way execution's real position would close - a stop-loss/target hit (checked against each subsequent bar's high/low), the strategy's own `square_off_time`, or, with nothing more specific configured or triggered yet, the next opposite-direction signal. Both stop-loss methods are simulated (`percent` needs nothing extra; `previous_candle` fetches a second candle series at the strategy's `stop_loss_interval`, reusing the main series when the two intervals match), as is `trailing_stop_enabled`. Response shape: `{"trade_count", "hypothetical_pnl", "trades": [{entry_time, direction, entry_price, exit_time, exit_price, exit_reason, pnl}, ...]}` - `exit_reason` is one of `stop_loss`/`target`/`square_off`/`opposite_signal`/`end_of_data` (still open at the end of the range, marked to the last available close). Still not a full sizing/account simulation against execution's real order logic (no position sizing, no lot sizes, no account balance) - see `docs/architecture.md`. It never changes `Strategy.status` automatically; promote `draft`/`backtesting` → `live` manually via `PATCH` once you're satisfied with the report.

For an `instrument_type='option'` strategy (crossover rules only today), `/backtest` transparently produces a **combined-premium** report instead: the same entry-signal timing as above, but each simulated trade tracks a bull-call-spread/bear-put-spread's combined leg premium (historical option data via Dhan's rolling-option endpoint) against combined SL/target instead of the underlying's own price - `entry_price`/`exit_price` are the combined premium, `exit_reason` additionally includes `combined_stop_loss`/`combined_target`, and each trade carries a `legs` field. See `docs/architecture.md` § "Backtesting option strategies (Phase 4c)" for the mechanics and its documented limitations (no OI-liquidity nudge, NSE/BSE-only data source, breakout/range-breakout rules not yet supported).

**Grid search** (`POST /strategies/{id}/backtest/grid?from=&to=`, body `{"param_grid": {"period": [7, 14, 21], "sma_period": [5, 9, 14]}}`) sweeps the strategy's indicator across every combination of the given candidate values and reports the same trade-simulated P&L per combination (same SL/target/square-off applied to every combination), sorted best-first - a param left out of `param_grid` stays fixed at the indicator's own current value. One candle-history fetch covers the whole grid (sized for the widest warm-up any combination needs), and an invalid combination (e.g. a period below RSI's minimum) shows up as an `error` row instead of failing the request. Capped at 100 combinations per call. Read-only - it never edits the `Indicator` row; `PATCH /indicators/{id}` once you've picked a winner. The frontend's In-house tab exposes this directly under the single-backtest panel.

**Regime filter** lives on the Rule now (`Rule.regime_indicator_ids`), not the Strategy - 5 dedicated `Indicator` types (`structure`, `efficiency_ratio`, `adx`, `dmi_direction`, `ema_slope`, alongside the pre-existing `rsi`), each independently created/reused like any other Indicator, gate a rule's own bias (ALL listed ones must confirm) before it fires - via `app/domain/regime.py`'s underlying math (`check_structure`/`check_efficiency_ratio`/`check_adx`/`check_dmi_direction`/`check_ema_slope`). Computed single-timeframe, on the rule's own `interval` - no separate higher-timeframe fetch. Both the live engine tick and `/rules/{id}/backtest` apply the exact same gate, so a backtest report reflects what the live engine would actually do; it also now applies to all 3 rule types (crossover/breakout/range_breakout), where it previously only covered two. See `docs/architecture.md` § "Market regime filter."

## Breakout: a second, structurally independent rule type

Beyond crossover, a strategy's `rule_config` can instead be `{"type": "breakout", "htf_interval", "htf_breakout_period", "ltf_interval", "ltf_breakout_period", "ema_filter_enabled", "ema_period"}` - a multi-timeframe Donchian breakout with no `Indicator` involved at all, implemented in its own module (`app/domain/breakout.py`) rather than through `rules.py`/`indicators.py`, since it needs two candle series and owns its own exit logic (see `docs/architecture.md` § "Multi-timeframe Donchian breakout"). A higher-timeframe (HTF) N-bar high/low breakout arms an entry window valid only until the next HTF candle closes; within that window, the first lower-timeframe (LTF) candle to itself break its own N-bar high/low triggers entry, with the confirming HTF candle's low/high as a static initial stop. A separate reversal exit (single-bar HTF flip, LTF-confirmed) closes the position - never flips into a new one - but **only in the backtest**: execution has no live mechanism for it today, so the live engine only ever posts entries. The initial stop-loss *is* enforced live, by reusing execution's existing `previous_candle` method (`stop_loss_interval` auto-set to the rule's own `htf_interval` at create time) - which is why `htf_interval` must be one of execution's supported stop-loss intervals (1/5/15/25/60min), a narrower set than the general `Interval` type HTF/LTF otherwise accept. `Strategy.interval` is required to equal the rule's own `ltf_interval`. Grid search doesn't support this rule type yet (`/backtest/grid` 422s for it) - only `/backtest` does.

Execution accepts `instrument_type='future'` orders from this engine (a deliberate pull-forward of what was originally scoped as a later phase - see `docs/architecture.md`) and sizes them in whole lots via `market-data`'s `GET /instruments/lot-size`. Trading options based on this engine's bias (rather than the interim active-month future) is still future work.
